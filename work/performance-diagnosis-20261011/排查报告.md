## 共性原因与证据边界

1. **图片上下文持续变大。** 污水审片首次请求约33,741 input tokens，最后约170,899；抹茶审片从19,605到121,918。两个角色都已使用`fork_turns=none`，不是误复制全部主聊天；后续图片、原尺寸图、工具输出和跟进消息仍会持续增加上下文。缓存命中较高，累计input tokens不能当作实际收费或未缓存工作量。输入增长与间隔变长同时存在，尚不能证明全部延迟由上下文引起。
2. **独立审核是串行交付门槛。** 主角色等待审片者；审片者又可能等全帧证据、brief或补充资料。抹茶首审开始时证据未就绪，审片者另导出reviewer_frames，原来的qa/r1/frames也存在，出现重复证据准备。其余阶段没有可执行工作时，重复催促/等待不产生制作进展。
3. **每个版本都增加一次全帧工作。** 污水计划包括1125帧预演、600帧正式样段、2250帧正式片，合计3975帧，尚不含修复；抹茶三版各150帧。全帧/完整音频是用户要求，不能改为关键帧抽查，但阶段数量和版本数量会影响总等待。
4. **能力限制与交付停止条件未充分收敛。** 项目已知道真实听音不可用，最终结论应保持incomplete；不应为无法获得的听音能力继续等待或返工。两轮修复上限限制返工次数，没有直接限制审片者长时间不返回。已看完画面后仍需核对brief与写报告，完成这些可做项后应交付当前版本及限制。
5. **预演存在可避免的高分辨率工作。** 污水render.mjs用1080×1920 viewport渲染，再在capture里缩到540×960；拿破仑render-v3.mjs也固定1080×1920 viewport再缩图。低清模式因此不是完整的低清渲染。污水当前只用了约64秒取图，此项是次要优化，不应承诺它能消除两个小时的审核等待。
6. **素材缺陷导致必要返工。** 拿破仑姿态表相邻鞋尖相连、均分裁格残留其他行等问题需要重新分离或补图；它们是实际资产问题，不是提高编码线程能解决的。

补充：污水首次按自定义video_reviewer类型派工返回`agent type is currently not available`，随后改普通独立角色成功；两次调用相隔约133秒。它造成一次交接损耗，不足以解释整个审核时长。当前项目模型配置已撤回，所读制作/审片会话记录为Astra Medium；没有证据把本次慢归因于Sol High默认。

两个采样均未找到三个项目正在运行的render/ffmpeg进程。约16GB物理内存，可用约5.7–6.4GB；性能计数器一次CPU样本为0%。这说明采样时未在重负载编码，不证明历史上没有资源竞争。没有记录到可据以判定429、模型限流或网络重试的错误事件；不能将“没记录到”写成“这些问题绝不存在”。

## 建议的处理顺序

1. **先减少审核会话的累积与交接。** 全帧证据就绪再启动；第一次盲看后一次交付brief/声音事件/来源入口。按镜头或连续区间维护短覆盖账本，在需要时用独立、最少上下文的审片角色接续，合并边界和覆盖，避免一位审片者携带所有历史图片反复往返。保持当前模型与推理，不为速度自动切换。
2. **给无进展审核明确的交付边界。** 每批返回覆盖/缺陷/下一范围；连续没有新的观察或工具结果时定位限制，先保存已有记录。能力不可用则在完成可做检查后展示当前可播放版并标注审核未完成，不假报通过、不把主角色自查当独立审片，也不通过换角色重置两轮上限。具体等待时长应由用户接受的制作时限决定。
3. **减少重复版本和可合并阶段。** 摄影/布局数值约束先检查再导出，避免因几何安全区问题多生成版本；简单短片可用整片承担正式样段。长片仍保留确有必要的预演和关键样段，每个已生成版本照常审核。
4. **再优化渲染与素材。** 预演按实际输出尺寸建渲染缓冲，采用统一逻辑坐标，保持字幕布局一致；取帧复用已存在且哈希对应的证据。动作表生成后立即做透明间隙、格间隔离和接触锚点检查，早点发现必须补生的资产。正式画幅维持1080×1920。
5. **记录阶段用时。** 导出分别记录加载、取帧、编码、解码、证据准备；审片记录每批发出/返回与待审范围；任务检查点同步真实产物。这样才能区分渲染、模型等待和人工反馈，而不是一直显示“正在生成”。
