# 从题材到运动

## 选择有内容的视觉机制

不要从“做三张漂亮卡片”开始。先确定变化是什么，再选怎样让观众看到它。

| 要表达的关系 | 可用机制 | 需要检查 |
|---|---|---|
| 原因导致结果 | 接触、传递、连锁响应 | 动作顺序是否能被读懂 |
| 分散形成结构 | 粒子/物体聚合，连接逐步建立 | 聚合后的状态是否有意义 |
| 一个系统包含多个部分 | 从局部拉开，空间导航，剖面 | 关系和层级是否清楚 |
| 对比或转变 | 同一物体连续变形、对齐后比较 | 对应关系是否持续可见 |
| 数据变化 | 轴与单位稳定，数值驱动形状 | 数据真实，尺度一致 |
| 数学/科学 | 可执行过程、几何变化、状态演化 | 教学演示与真实模拟需区分 |
| 字词的含义 | 字形变成对应物，排版参与动作 | 阅读时间，中文字体与分行 |

每个段落有一个主要动作；次要运动用于接触反应、惯性或注意引导。文字补充无法仅由运动解释的信息，不代替画面完成所有叙事。

## 动作的起承转合

根据动作选择预备、加速、接触、余动和落定。重量大的物体可以缓启动，接触时快，落定后有轻微余动；细线生长可以匀速，以免误导过程；相机通常避免弹簧回弹。不要给所有元素同一组 spring 或同一种入场。

运动方向和曲率要一致。轨迹交接点的位置连续；需要柔和交接时速度也连续。遮挡或短快切可以掩蔽必要跳变，但不能用闪光遮盖所有代码断点。关键信息留出观众可以读懂的停留。

## 连续世界与相机

需要展示空间关系时，把元素放在共享世界坐标，相机先看局部行为，再展示结果或系统。二维相机正确形式：

```text
screenX = viewportWidth/2 + (worldX - cameraX) * zoom
screenY = viewportHeight/2 + (worldY - cameraY) * zoom
```

实现为先平移到视口中心，再缩放，再平移负的相机位置。检验：世界中的相机焦点必须始终投到视口中心，任何 zoom 都成立。HUD 与字幕若应固定在屏幕上，放在相机外层。

远景与近景应由构图需求决定；不能只把整页放大缩小冒充有内容的运镜。相机移动期间控制可读文字与主体动作的竞争。

## 解析三维和真实三维

解析投影可轻量表现球体点云、轨迹、分子示意、空间网络。旋转后按深度排序，视距与近裁剪面保持安全。后方粒子更小、更淡，前方粒子更清晰。该方法不自动提供灯光、真实遮挡或物理。

需要复杂模型、材质、阴影、遮挡或摄影机穿行时转到 Three.js。物理状态应预计算或由解析式得到，不能依赖之前是否渲染过第 N 帧。

## 字体与构图

选择符合题材的字体，加载完成后才测量。中文不以英文宽度估算；标题、数据、标注的层级与字距要分别设计。预览缩到实际观看尺寸，检查最小文字、字幕安全区、边缘裁切和对比度。构图可以故意裁切装饰或大字，核心信息不能被裁。

## 声音

先决定是否需要旁白、配乐、拟音或无声，再安排事件。转场铺垫音引出动作，接触音落在接触点，余音不掩盖旁白。切换不是每次都需要 impact。用户给定音乐时分析真实拍点；原创测试音轨可用明确事件表生成，不能将音效序列称为高质量原创配乐。

## 观察清单

- 开始时是否已经有可读的主体或动作？
- 运动揭示了什么关系？是否只是摆放文字？
- 转场前后的主体位置、速度、色彩或形状是否有连接？
- 相机是否引导注意，重要动作是否在其停留时完成？
- 中间状态是否空、乱、难读、穿帮？
- 数据/标签是否有依据，文字是否溢出，字体是否加载？
- 声音与接触、切点一致吗？结尾是否落定？
- 关键动态是否真实检查过？哪些判断目前只有静帧支持？

写缺陷时给时间/帧号和可见现象，不用笼统“更高级”。
